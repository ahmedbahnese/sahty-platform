# برومبت تنفيذ تحسين واجهة منصة Sehaty على Replit

أنت تعمل كمهندس **UI/UX Senior** ومهندس **Frontend/Full‑Stack Production Engineer** على منصة الرعاية الصحية Sehaty. المطلوب تنفيذ تحسين حقيقي داخل المشروع الحالي، وليس إنشاء نموذج شكلي أو صفحات وهمية. يجب أولًا فحص الكود الحالي وتشغيل المشروع وفهم بنية React/Vite وFlask وواجهات API قبل تعديل أي ملف.

## الهدف الرئيسي

أعد تصميم الواجهة بالكامل لتكون منصة طبية احترافية، موحدة، منظمة، ومتجاوبة بصورة صحيحة على الهاتف والتابلت والكمبيوتر. يجب أن يشعر المستخدم أن جميع الصفحات جزء من منتج واحد له هوية بصرية ثابتة، مع إظهار قائمة التنقل العلوية المناسبة بعد تسجيل الدخول بحسب نوع المستخدم وصلاحياته.

يجب الحفاظ على البيانات الحقيقية، وربط جميع الصفحات بواجهات API الحالية، وعدم إضافة بيانات تجريبية أو Mock Data أو أرقام وهمية. لا تغيّر قواعد الصلاحيات أو حماية الموارد أو المصادقة إلا إذا اكتشفت خطأ واضحًا، وفي هذه الحالة أصلحه مع إضافة اختبار يثبت الإصلاح.

## المرحلة الأولى: الفحص قبل التعديل

نفّذ أولًا فحصًا موثقًا للمشروع، وتحقق من الملفات التالية أو ما يعادلها في بنية المشروع:

- ملف تشغيل التطبيق وملفات إعداد Vite وReact.
- مكونات `Navbar` و`Sidebar` و`Footer` وملف التخطيط الرئيسي.
- صفحات تسجيل الدخول والتسجيل والصفحة الرئيسية ولوحات التحكم.
- `AuthContext` أو نظام الجلسات الحالي.
- قائمة الأدوار والصلاحيات الموجودة في الواجهة والخادم.
- جميع المسارات والـ API endpoints المستخدمة في عرض الأطباء والمنشآت والمواعيد والملفات الطبية.
- إعدادات Replit و`PORT` وCORS وملفات البناء والتشغيل.

قبل التنفيذ، أنشئ تقريرًا مختصرًا يوضح: ما هو الموجود، ما هو سبب عدم ظهور القائمة بعد تسجيل الدخول، ما الصفحات التي تستخدم تخطيطًا مختلفًا، وما التعديلات التي ستنفذها.

## المرحلة الثانية: الهوية البصرية الموحدة

اعتمد هوية طبية هادئة واحترافية تناسب البيانات الصحية. استخدم لوحة ألوان موحدة تعتمد على الأزرق الطبي والفيروزي والأبيض والرمادي الفاتح، مع ألوان واضحة للحالات مثل النجاح والتحذير والخطأ والطوارئ. لا تستخدم ألوانًا عشوائية مختلفة بين الصفحات.

اعتمد خطًا عربيًا واضحًا مثل Cairo أو Tajawal، وطبّق RTL بصورة صحيحة على كل الصفحات والنماذج والجداول والقوائم. وحّد شكل الأزرار والبطاقات وحقول الإدخال والعناوين والتنبيهات وحالات التحميل والرسائل الفارغة.

استخدم نظام تصميم مركزيًا يتضمن متغيرات للألوان، وأنصاف أقطار البطاقات، والظلال، والمسافات، وسرعة الانتقالات. لا تكرر CSS غير الضروري داخل كل صفحة. استخرج المكونات المشتركة مثل:

- `AppShell` أو التخطيط العام.
- `TopNavbar`.
- `RoleSidebar`.
- `PageHeader`.
- `StatCard`.
- `SectionCard`.
- `LoadingState`.
- `EmptyState`.
- `ErrorState`.
- `ResponsiveTable` أو تخطيط بديل للجداول على الهاتف.

## المرحلة الثالثة: القائمة العلوية بعد تسجيل الدخول

هذه نقطة أساسية ولا تعتبر المهمة مكتملة دون تنفيذها واختبارها.

بعد تسجيل دخول المستخدم بنجاح، يجب أن تظهر له قائمة تنقل علوية واضحة وثابتة في جميع الصفحات المحمية. يجب ألا تختفي القائمة بسبب شرط CSS أو اختلاف اسم الدور أو إعادة التوجيه.

يجب أن تحتوي القائمة العلوية على:

1. شعار Sehaty والعودة إلى لوحة التحكم.
2. اسم المستخدم أو اسم المنشأة مع صورة أو الحرف الأول.
3. الدور الحالي للمستخدم، مثل: مريض، طبيب، تمريض، صيدلية، معمل، مركز أشعة، مستشفى، مدير.
4. روابط الوظائف المسموح بها لهذا الدور فقط.
5. زر إشعارات إذا كان endpoint الإشعارات متاحًا.
6. زر الإعدادات والملف الشخصي.
7. زر تسجيل الخروج يعمل فعليًا وينهي الجلسة.
8. زر تبديل الدور فقط إذا كان المستخدم يمتلك أدوارًا متعددة ومصرحًا له بذلك.
9. قائمة هاتف قابلة للفتح والإغلاق، مع `aria-label` و`aria-expanded` وحركة بسيطة غير مزعجة.
10. قائمة فرعية أو زر `المزيد` للوظائف التي لا تتسع في العرض المتوسط.

طبّق هذا السلوك حسب الدور:

| الدور | الوظائف الرئيسية التي تظهر له |
|---|---|
| المريض | لوحة التحكم، الأطباء، المواعيد، الملف الطبي، الوصفات، الأدوية، التحاليل، الأشعة، بنك الدم، الطوارئ، الإعدادات |
| الطبيب | لوحة التحكم، مواعيد المرضى، الوصفات، طلبات التحاليل، طلبات الأشعة، الملف الشخصي، الإعدادات |
| التمريض | لوحة التحكم، المواعيد، خدمات التمريض، الملف الشخصي، الإعدادات |
| الصيدلية | لوحة التحكم، الوصفات، متابعة الأدوية، الطلبات، الإعدادات |
| المعمل | لوحة التحكم، المواعيد، طلبات التحاليل، النتائج، الإعدادات |
| مركز الأشعة | لوحة التحكم، المواعيد، طلبات الأشعة، التقارير، الإعدادات |
| المستشفى | لوحة التحكم، المواعيد، التحاليل، الأشعة، الأقسام والخدمات، الإعدادات |
| المدير | لوحة الإدارة، المستخدمون، الجهات الطبية، التقارير، التدقيق، الإعدادات |

لا تعرض رابطًا لمستخدم لا يملك صلاحية الوصول إليه. وفي الوقت نفسه، لا تجعل إخفاء الرابط هو وسيلة الحماية الوحيدة؛ يجب أن يستمر الخادم في تطبيق Authorization وRole Validation وOwnership Protection.

## المرحلة الرابعة: التخطيط المتجاوب

طبّق التصميم Mobile‑First مع نقاط استجابة واضحة:

- الهاتف: عرض 320–639 بكسل. استخدم قائمة هاتف أو شريط تنقل سفلي للوظائف الأساسية، وبطاقات عمودية، وأزرار بعرض مناسب للمس.
- التابلت: عرض 640–1023 بكسل. استخدم قائمة قابلة للطي أو درجًا جانبيًا، وبطاقات من عمودين، وقائمة علوية مختصرة.
- الكمبيوتر: عرض 1024 بكسل فأعلى. استخدم القائمة العلوية الكاملة أو القائمة الجانبية الثابتة بحسب نوع الصفحة، مع مساحة محتوى منظمة.

يجب منع horizontal overflow في جميع الصفحات. تأكد من أن الجداول تتحول إلى بطاقات أو يمكن تمريرها أفقيًا داخل حاوية محددة فقط، وأن النوافذ المنبثقة لا تتجاوز الشاشة، وأن حقول الإدخال لا تسبب تكبيرًا مزعجًا على iOS، وأن شريط التنقل لا يغطي المحتوى.

## المرحلة الخامسة: توحيد الصفحات

وحّد الغلاف العام لكل الصفحات المحمية ليحتوي على القائمة العلوية، وترويسة الصفحة، ومسار تنقل عند الحاجة، ومحتوى الصفحة، ورسائل التحميل والخطأ والحالة الفارغة.

وحّد الصفحات العامة مثل الصفحة الرئيسية، الأطباء، الدليل الطبي، المستشفيات، الصيدليات، المعامل، مراكز الأشعة، بنك الدم، الخدمات، والطوارئ. يجب أن تستخدم نفس Navbar ونفس Footer ونفس التدرج البصري.

وحّد لوحات التحكم لجميع الأدوار باستخدام مكونات مشتركة دون إزالة الوظائف الحالية. يجب أن تعرض الإحصاءات من API الحقيقي، وأن تتغير البطاقات والروابط حسب الدور الفعلي للمستخدم.

## المرحلة السادسة: التفاعلات وتجربة الاستخدام

أضف الحالات التالية لكل عملية API: تحميل، نجاح، فشل، وعدم وجود بيانات. لا تعرض رسالة "لا توجد بيانات" إذا كان السبب الحقيقي هو فشل الاتصال بالخادم؛ اعرض رسالة اتصال واضحة مع زر إعادة المحاولة.

أضف انتقالات بسيطة لا تتجاوز 300ms، واحترم `prefers-reduced-motion`. أضف حالات focus واضحة للوحة المفاتيح، واجعل جميع الأزرار والروابط قابلة للاستخدام عبر لوحة المفاتيح. لا تستخدم animations مبالغًا فيها في تطبيق طبي.

## المرحلة السابعة: البيانات والـ API

لا تنشئ Mock Data. افحص كل fetch أو API call في الصفحات وتأكد من:

- استخدام endpoint صحيح.
- إرسال Authorization عند الحاجة.
- معالجة 401 بإعادة المستخدم إلى تسجيل الدخول بصورة سليمة.
- معالجة 403 برسالة صلاحيات واضحة.
- معالجة 5xx برسالة خادم وزر إعادة المحاولة.
- عدم فقدان البيانات عند تغيير حجم الشاشة أو فتح القائمة.
- استمرار البيانات بعد إعادة تحميل الصفحة.

## المرحلة الثامنة: الاختبارات المطلوبة

أضف أو حدّث اختبارات تلقائية تشمل على الأقل:

1. تحميل الصفحة الرئيسية دون أخطاء.
2. عدم وجود horizontal overflow عند عروض 375 و768 و1024 و1440 بكسل.
3. ظهور Navbar العام على الصفحات العامة.
4. ظهور Navbar المستخدم بعد تسجيل الدخول.
5. ظهور روابط الدور الصحيح وعدم ظهور روابط دور آخر.
6. فتح وإغلاق قائمة الهاتف والتابلت.
7. ظهور اسم المستخدم والدور الحالي.
8. نجاح تسجيل الخروج.
9. الانتقال من CTA إلى التسجيل أو تسجيل الدخول.
10. عدم تغطية شريط التنقل السفلي للمحتوى على الهاتف.
11. ظهور حالات loading وerror وempty بصورة صحيحة.
12. استمرار عمل الصفحات بعد إعادة التحميل.

استخدم Playwright أو إطار UI موجودًا في المشروع. اجعل الاختبارات قابلة للتشغيل محليًا وفي CI، وأضفها إلى أمر الاختبار الرئيسي. لا تعتبر نجاح build وحده دليلًا على نجاح الواجهة.

## المرحلة التاسعة: التحقق النهائي

بعد التنفيذ شغّل:

```bash
npm run lint
npm run build
npm run test:backend
npm run test:ui
```

إذا كانت أوامر المشروع مختلفة، استخدم الأوامر المكافئة وسجّلها. اختبر كذلك المسارات الأساسية يدويًا في المتصفح: الصفحة الرئيسية، تسجيل الدخول، لوحة المريض، لوحة الطبيب، الدليل الطبي، الأطباء، المواعيد، والملف الشخصي.

تأكد من أن الخادم يعمل على `0.0.0.0:$PORT` في Replit، وأن الواجهة تستخدم نفس origin أو إعداد CORS صحيح، وأن الصفحة لا تعتمد على localhost في الإنتاج.

## قواعد مهمة

لا تحذف وظائف موجودة دون سبب موثق. لا تغيّر مخطط قاعدة البيانات لمجرد تحسين الشكل. لا تضع أسرارًا أو مفاتيح API في الكود. لا تستخدم بيانات وهمية لإخفاء مشكلة API. لا تكتفِ بتعديل CSS إذا كانت المشكلة في المصادقة أو تحميل بيانات المستخدم. لا تعتبر المهمة منتهية حتى يظهر Navbar المستخدم بعد login فعليًا ويعمل تسجيل الخروج وتعمل روابط الدور الصحيح.

في نهاية التنفيذ أنشئ تقريرًا يحتوي على الملفات التي تغيرت، المشاكل التي تم إصلاحها، الأدوار التي تم اختبارها، أوامر الاختبار ونتائجها، وأي متطلبات متبقية في Secrets أو إعدادات Replit. بعد نجاح الاختبارات، نفّذ commit واضحًا وارفع التعديلات إلى GitHub دون حذف تاريخ المشروع.

## النتيجة المتوقعة

أريد تطبيق Sehaty بمظهر طبي احترافي موحد، يعمل بصورة متجاوبة على الهاتف والتابلت والويب، وتظهر فيه القائمة العلوية للمستخدم بعد تسجيل الدخول في كل الصفحات المحمية، وتعرض فقط الوظائف المسموح بها حسب الدور، مع بيانات حقيقية واتصال فعلي بالـ API، واختبارات تلقائية تمنع عودة مشاكل التجاوب والتنقل مستقبلًا.
